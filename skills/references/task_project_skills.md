# Shared Skill Library and Project Projection Migration

Use this contract to validate Project knowledge, migrate legacy Project Skill Pairs, generate or resolve the vault-level Shared Skill Library, and install its single native router.

## Invariants

- `notes/` is authoritative Project Knowledge and a dual-native Obsidian/OKF v0.2 bundle; generated skill packages are disposable projections.
- The bundle-root `notes/index.md` declares only `okf_version: "0.2"` and groups concepts for progressive disclosure.
- Every other note starts with YAML on line 1, has a non-empty `type`, and uses relative standard Markdown links.
- Each Project has an immutable `project_id` and exactly `{PROJECT_ID}-usage` plus `{PROJECT_ID}-development`.
- Usage projects stable `audience: usage` and `audience: both` notes.
- Development projects stable `audience: development` notes and requires Usage for consumer and shared behavior.
- A stable note without `audience` is Unscoped Knowledge and remains Development-only until reviewed.
- Specs and logs never project directly. Distill durable behavior into stable notes first.
- Both skills describe the same `working_state` from `ProjectEntry.md`.
- The generated `skills/` tree is also OKF v0.2 conformant. Publication and installation are atomic; never edit canonical or installed projections.
- Every Project has a vault-only `mathdocs/` directory with the reserved `index.md`; paired derivations never project into Usage or Development skills.
- Substantive source/docs/vault/config/experiment changes select an approved Story hierarchy or standalone Quick Task before writing. Draft planning/initialization has only bounded record-first outputs; PRD success never approves code.
- Read-only questions/checks are record-free, with no durable cleanup/publication. Pass explicit sessions to mutating commands; never store selection in a shared pointer.
- Native adapters and pointer instructions carry the same limits. Installation needs a separately approved target plan, including isolated homes; never edit installed user-authored skills.

## Projection-Eligible Note Metadata

```yaml
type: Project Knowledge
status: stable
audience: development | usage | both
usage_stale: false
# stale_after: 'YYYY-MM-DD'  # optional real effective date
```

`usage_stale: true`, `draft`, `deprecated`, a reached `stale_after`, or material outside `notes/` excludes the document. The Projection CLI copies eligible note bodies under fresh OKF frontmatter and records source path and SHA-256 provenance in each topic reference.
Stable regular notes may declare `derivations: [mathdocs/{slug}.py]`; their authoritative display equations must match checked MathDoc result markers. Use Task M and `check-math` rather than hand-editing generated results.

## Shared Library Commands

Resolve `{KOSMIC_SKILL_DIR}` to the installed Kosmic Orchestrator skill and `{VAULT}` to the vault containing sibling `Projects/` and `Skills/`. The checked mutating commands below (`generate-library`, `migrate-library`, `generate`, `install-library`) require `--work-record "{QUALIFIED_RECORD}"` — the qualified identity of an approved governing record — on every invocation; selection is never cached across commands.

```bash
# Rebuild disposable catalog, manifest, domain indexes, and root router.
python3 {KOSMIC_SKILL_DIR}/scripts/kosmic_project_skills.py generate-library \
  --vault "{VAULT}" --work-record "{QUALIFIED_RECORD}"

# Validate authoritative domain/topic documents and exact generated bytes.
python3 {KOSMIC_SKILL_DIR}/scripts/kosmic_project_skills.py validate-library \
  --vault "{VAULT}"

# Produce a canonical hash-pinned plan. Omitted intent defaults to `understand`
# unless exactly one explicit intent signal is present. Add `--include-evidence`
# only when dated support is required outside `investigate`.
python3 {KOSMIC_SKILL_DIR}/scripts/kosmic_project_skills.py resolve-library \
  --vault "{VAULT}" --project "{PROJECT_ID}" --role usage|development|auto \
  --intent do|check|understand|investigate --include-evidence --query "{TASK}" \
  --max-bytes 32768 --max-domains 4 --max-topics 8

# Recheck every plan/source hash and emit the ordered Recipe Packet.
python3 {KOSMIC_SKILL_DIR}/scripts/kosmic_project_skills.py load-library \
  --vault "{VAULT}" --plan "{PLAN_JSON}"

# Migrate only an explicit source → assignment map. Every assignment declares
# target_id, artifact_role, and all five typed relationship arrays.
python3 {KOSMIC_SKILL_DIR}/scripts/kosmic_project_skills.py migrate-library \
  --vault "{VAULT}" --project "{VAULT}/Projects/{TARGET}" \
  --assignments "{ASSIGNMENTS_JSON}" \
  --work-record "{QUALIFIED_RECORD}"
```

Domain Topics declare `artifact_role: procedure|guideline|knowledge|evidence` independently of `audience`. Typed edges are `requires_procedures`, `governed_by`, `uses_knowledge`, `supported_by`, and evidence-only `supersedes`. `do` selects only procedures and fails with `NO_EXECUTABLE_MATCH`; `check` prefers guidelines then procedures, `understand` prefers knowledge then guidelines, and `investigate` prefers current dated evidence then knowledge. Recipe Packets label every topic by role and relation; evidence loads only for `investigate`, an exact evidence route, or `--include-evidence`.

Resolution is all-or-none. Ambiguity, stale hashes, unknown/cyclic dependencies, invalid audience edges, or byte/domain/topic overflow emits no Recipe body. `load-library` never re-ranks. Domain `SKILL.md` files load dynamically through the plan; detailed Usage/Development topics remain ordinary Markdown.

```bash
python3 {KOSMIC_SKILL_DIR}/scripts/kosmic_project_skills.py migrate \
```

Migration is restartable and transactional for `notes/`. It moves frontmatter to line 1, adds `type`, maps legacy `validated` to `stable`, conservatively maps undated legacy `stale` to `draft`, renames `TOC.md` to `index.md`, and converts unambiguous Wikilinks to relative Markdown links. Ambiguous links, embeds, and block references stop migration without partial note edits. Publication remains blocked until real stable Usage knowledge exists.

## Subproject Flat-Spec Migration

Migrating flat feature specifications into owner-aware subprojects is a deterministic, fully planned pipeline. Every stage runs fixed Python commands; no model calls review, approve, apply, or verify the migration, and no plan output is itself approval.

Workflow (each stage is a separate command; never combine planning and application):

1. **Plan.** `migrate-subprojects-plan --project "{PROJECT}" [--assignments file.json] [--output plan.json]` prints the proposal JSON and optionally saves it exclusively to `plan.json` (exclusive creation, no symlink following). `--output` produces bounded planning output, not unchecked migration authority: a saved plan file authorizes nothing by itself.
2. **Record and approve.** Create one shared Quick Task governing the migration with `spec-create --project "{PROJECT}" --kind quick-task --title "Subproject flat-spec migration"`, review its plan attachment and declared scope (plan outputs, deletions, and STATUS target), then move it through the standard Quick Task approval gate of `task_quick_task.md`. Approval must record the plan's exact `digest` value. Application re-derives the plan fingerprint under the governing record; the `--approve-digest` value must come from this approved record, never from an unapproved plan print or file.
3. **Apply.** `migrate-subprojects-apply --project "{PROJECT}" --plan plan.json --approve-digest "{DIGEST}" --work-record "{QUALIFIED_RECORD}"`. The executor recomputes the identical plan deterministically and refuses to run when the recomputed plan or its digest differs from the approved values — including when the vault changed since planning.
4. **Verify.** Re-run `migrate-subprojects-plan` (read-only; no `--output` needed) and confirm an empty or expected residual proposal, then run the standard validation commands (`validate`, `check-completion`).
5. **Recover (only after an interrupted apply).** `migrate-subprojects-recover --project "{PROJECT}" --plan plan.json --approve-digest "{DIGEST}" --work-record "{QUALIFIED_RECORD}"` completes the same approved plan idempotently.

Boundaries:

- **Regeneration:** plans printed under the old planner schema are not applicable. Regenerate with the current `migrate-subprojects-plan` and re-approve the new digest before applying.
- **Idempotence:** apply and recover are idempotent against the same approved plan; outputs already matching the plan are left untouched and verified by hash rather than rewritten.
- **Authority:** the plan defines the complete set of written paths (`outputs` and `deletions` are Project-relative) and the bound STATUS target. Nothing outside the plan is written; the executor never performs whole-Project replacement and never creates deleted-file shims. An external (non-Project) bound STATUS is managed separately by the executor and is not an arbitrary write.
- **History:** the plan records existing subprojects, inputs, and `before_sha256`/`after_sha256` hashes as its evidence of record; keep the approved plan file with the Quick Task for audit. Migration does not rewrite Git history or pre-existing shared record identities.
- **Structured headers:** nested YAML mappings and sequences, including `sources` entries with their own `title` and `url`, remain structured. Duplicate keys are rejected within the same mapping, not across different source entries. Both Markdown readers use the same safe parser; unsafe YAML tags, anchors and unsupported constructs fail explicitly.
- **URL preservation:** local destinations are matched using decoded URL paths, then rewritten with their query, fragment and Markdown title preserved. YAML `url` leaves, including nested source URLs, participate. External schemes and network-relative URLs remain unchanged; code spans and fenced examples are not rewritten.
- **Link correction:** each authoritative Project Markdown file is checked against the final candidate file inventory. A broken internal path is repaired only when its filename or stem identifies a unique candidate, including an old moved-record filename. Valid references are retained. `link_corrections` records old/new destinations and the resolution basis; `link_problems` reports unmatched or ambiguous candidates. Ambiguous editable references block application rather than guess.
- **Protected documents:** evidence, logs, generated skill Markdown and `specs/skill-proposals/inputs/` (input manifests and curated snapshots) are hash-pinned, audited and reported with `protected: true`, but never rewritten. A copied template with nonparseable placeholder frontmatter produces an `unparsable-document` report, not an authoritative-record parse failure. Generated projections must be regenerated through their supported workflow; proposal input snapshots retain the bytes required by their manifests.
- **Target recognition:** existing protected Markdown files are valid link targets, but never filename/stem repair candidates. Moved authoritative documents rebase links to those files without editing their contents. Table WikiLinks preserve an escaped alias separator (`\|`) and fragment. Markdown reference definitions must start the physical line (at most three leading spaces); mid-line prose citations and text following an inline code span are not definitions.
- **Ancestry precedence:** `linked_*` values prefer a valid document-relative target before a same-named Project-root target. If no document-relative target exists, legacy Project-relative metadata still resolves. In particular an existing owner's `SubprojectEntry.md` keeps `linked_prd: "specs/prd.md"` pointing to its own PRD, not a moving root-level PRD.
- **STATUS binding:** a Project with a bound `status_root` has its `STATUS.md` regenerated as part of the plan outputs (hash-checked before rewrite). An unbound Project has `status_binding.disposition: unbound` and no STATUS write. Staged STATUS rendering rebases catalog links onto the final Project root; pending-receipt completion is always evaluated against the Project root, never the staging tree.
- **Recovery conflict policy:** recover refuses to run when the Project state matches neither the pre-plan nor the post-plan fingerprint of the approved plan (for example, unrelated edits landed after the interruption), when the digest no longer matches, or when the plan file was modified. Resolve by regenerating, re-approving, and re-planning; never hand-edit partially applied outputs.

Execute and compare active Math Derivations without changing files:

```bash
python3 {KOSMIC_SKILL_DIR}/scripts/kosmic_project_skills.py check-math \
  --project "{VAULT}/Projects/{TARGET}" [--slug "{SLUG}"] [--timeout 30]
```

After reviewing a derivation change, add `--update --source-root "{SOURCE_ROOT}"` to refresh all selected paired-note metadata and generated result regions atomically.

Check a story or quick task before completion:

```bash
python3 {KOSMIC_SKILL_DIR}/scripts/kosmic_project_skills.py check-completion \
  --project "{VAULT}/Projects/{TARGET}" \
  --work-item "{WORK_ITEM}" \
  --source-root "{SOURCE_ROOT}" --work-record "{QUALIFIED_RECORD}"
```

Work items must declare `consumer_interface_change: true | false`, `proposal_required: true | false`, `routine_edge_change: true | false`, and `routine_decision_required: true | false`. Any work item that adds or changes a procedure's `uses_routines` edge declares `routine_edge_change: true`; completion then requires `routine_decision_required: true`. A required skill proposal uses exactly one `skill_proposal` path. A required routine decision uses non-empty `routine_proposals`, one validated, non-pending Task P artifact per unique proposal path; a false decision gate requires the list to be empty. Consumer Interface changes require current stable `usage` or `both` notes and a drift-free canonical pair. Declared `evidence_packs` must exist and be linked from a draft-or-stable note.

Math-derived work items declare both `derivations: [{slug}, ...]` and `math_implementation_files: [relative/path, ...]`. Each listed file must remain under `--source-root` and contain a matching `MathDoc: {project_id}/{slug}[#result-name]` identifier.

`validate` additionally checks the Experience layer: every Evidence Pack's `MANIFEST.md` (kind `execution|research`, `produced_by`, ISO `date`, non-empty `summary`, and a body file-role list matching the pack contents exactly) and the `impact.md` ledger's fixed six-field entries. Evidence packs and the ledger live outside `notes/` and never project into the Skill Pair; `generate` appends publication entries to the ledger after each atomic publication.

MANIFEST frontmatter may optionally carry code provenance: `git_head` (commit
hash) and `worktree_tree` (tree hash or `clean`). Present ⇒ both required and
shape-checked (40/64 lowercase hex). Use the `provenance` command
(`--repo PATH`, default cwd) to print paste-ready lines computed via a
temporary index — no working-tree or index side effects.

Projected reference bodies are package-consistent: a Markdown link whose target is not projected into the same Skill Pair package (draft target, other-audience target) is demoted to bold plain text, and `generate` warns on stderr naming each demoted link. Links inside code fences, external URLs, and non-Markdown targets are untouched.

Generate and validate the routine inventory from static source declarations, or query it before implementing repeated mechanics:

## Install Adapters

Install one native Shared Skill Router and remove managed per-Project Usage/Development packages only after byte and identity verification. Installation keeps its own approved adapter plan: the record that approved library generation does not authorize installation.

```bash
python3 {KOSMIC_SKILL_DIR}/scripts/kosmic_project_skills.py install-library \
  --vault "{VAULT}" \
  --adapter opencode|claude-code|codex|omp \
  --home "{HOME}" \
  --work-record "{QUALIFIED_RECORD}"
```

Verify the installed router and absence of managed legacy pairs:

```bash
python3 {KOSMIC_SKILL_DIR}/scripts/kosmic_project_skills.py check-library-installation \
  --vault "{VAULT}" \
  --adapter opencode|claude-code|codex|omp \
  --home "{HOME}"
```

Installation reports only on-disk success. Reload or start a new adapter session and inspect its skill inventory before claiming activation. The inventory must contain `memnotes-skills`; ABINIT, TB2J, Kosmic, and other Domain Skills are dynamically loaded vault documents and must not appear as separate native skills. A collision with an unmanaged `memnotes-skills` path or any failed copy/removal/verification preserves the prior complete inventory.

## Explicit work records and receipt completion

Use `work start --project PROJECT_ROOT --worktree ROOT --work-record REF` before writable work. It resolves the record and refuses any dirty worktree. No work session, handle, lease, delegation, or shared active-task pointer exists. Use one clean worktree and one writer per record.

Each supported mutating command takes `--work-record REF` and rechecks ownership, ancestry, and lifecycle. Command-declared derived outputs (Skill Pair, STATUS, ledger, adapter files) inherit the record; no per-output scope grant is issued. Raw shell/editor writes remain agent compliance, not an OS sandbox.

Before constructing proof or running finish, load [Receipt completion](work_completion.md). It is the authoritative reference for acceptance checklist syntax, contained artifact paths, actual review decisions, computed source revision, scope claims, terminal validation and owned-delta integration.

Completion requires the successful checked receipt, not a manually edited status. Report qualified identity, canonical path and observed results separately while completion remains pending.
