# Projection CLI experience commands

## Overview
How the Projection CLI treats executable MathDocs, Skill Proposals, projections, installation, derived STATUS, and record-embedded completion. Structural commands are deterministic, offline, and stdlib-only; `check-math` executes trusted Project Python and therefore requires the Project derivation environment. The command reference `skills/references/cli-projection-commands.md` owns flags and step-by-step procedures; this note carries the durable invariants.

## Principles
- Command success is authoritative for its documented outputs: use returned identities, paths and receipts directly, without a second administrative confirmation. Recovery follows actual errors; failure does not imply rollback, since completion publication is stepwise. This does not replace acceptance verification of newly changed software or scientific claims.
- Routine Project initialization creates no Quick Task and enters no implementation review or work-finish lifecycle. Its bounded authority covers setup only; changing initialization behavior still follows the development workflow, and migration, registration and installation retain their target approvals.
- Direct read-only inspection uses authoritative notes/specs without bootstrap or generated-state repair; missing identity, projections or router are reported, not silently created. Loading generated/routed guidance and executing or mutating Project state retain their normal prerequisites and live authority checks.
- Explicit idea capture is a bounded record-free write: `idea --project PROJECT_ROOT --text TEXT [--title TITLE]` saves under `ideas/`; `idea --vault VAULT_ROOT --text TEXT [--title TITLE]` saves under `GeneralIdeas/` without any Project identity. The selected root must already exist. Capture creates only the missing child directory and a new title-named idea, with complete content under dated History; repeated titles receive distinct numeric suffixes, never an overwrite. It needs no Git, initialization/repair, work record, review, receipt or session bookkeeping. Use the returned absolute `idea_path` directly; do not replay after an uncertain save. Developing the command or implementing an idea retains normal authority.
- Conversational `kosmic idea` resolves the configured/selected Project, or the vault for an explicitly general idea; ambiguity is clarified before saving, never silently reclassified. Preserve the supplied text and optional title, invoke once, return the actual absolute path as a full-label Markdown link and stop. The owning `task_idea.md` in the Kosmic skill provides both invocations and diagnostic-driven failure handling. Capture does not append, merge, curate, promote knowledge or approve implementation.
- Completion bookkeeping belongs to finish: one completion log, receipt-derived STATUS and status updates to existing canonical table rows. Native `spec-create` owns each new draft's record and correct owning-index row, returning explicit record/index paths and the operation ID; callers no longer construct those rows. Historical missing/bullet entries and non-native artifacts are not automatically migrated. Batch authored changes before the next freshness gate; do not add a duplicate completion log or refresh after success.
- Workflow questions resolve available facts before asking for decisions; an explicit artifact request authorizes drafting, never approval of its content. Requested/scheduled maintenance is separate from foreground work, and optional non-blocking suggestions do not automatically expand an approved task.
- Creation publication is stepwise and operation-backed for all five kinds. Resume the original incomplete operation with its original kind/owner/parent inputs; it retains the reserved identity, merges only its row into the current index and preserves unrelated content. Conflicting draft bytes, entries or unsafe paths refuse rather than overwrite; a fresh duplicate and an already-published operation are not resumable successes.
- Native rows merge only into a compatible Kind/Record/Status table; other human-authored layouts retain their bytes and receive a separate canonical table. Escaped title characters and physical row boundaries roundtrip through creation recovery and finish's status-only update.
- Creation and finish serialize their index read/merge/publication phases with the same creation lock. A detected external change refuses before replacement and preserves current bytes; an arbitrary editor ignoring the lock can still race the pre-rename content check. Interrupted finish remains stepwise and recovers through its existing retry path, without a new admission gate or transaction guarantee.
- Projected references are package-consistent: a link whose target is outside the rendering package (drafts, other-audience notes) is demoted to bold plain text and `generate` warns on stderr naming each demoted link; code fences, external URLs, and non-Markdown targets are untouched.
- Notes carry no `evidence:` gate: a stable note is never rejected for missing or unresolved evidence paths, and legacy `evidence:` frontmatter values remain valid historical metadata that current commands neither require nor bless (knowledge-first notes, `docs/adr/0004-knowledge-first-notes.md`). Reproducibility uses plain `sources:` links in the note body.
- Completion is record-embedded: criterion observations, the independent two-axis review, and scope claims live in the work record; `work finish` publishes a receipt bound to the completed record's bytes. One ordinary finish runs every completion gate — proof, finish-claim scope, review, and the same read-only precheck `check-completion` uses (dependencies, STATUS freshness, `consumer_interface_change`, math/proposal/routine, related notes, projection) — and refuses domain failures as `COMPLETION_PRECHECK_FAILED` with the original diagnostic retained; a pre-write freshness recheck rejects mid-episode record/source/authority drift without repinning. Receipt-bearing retries re-verify only fresh identity, the unchanged record bytes (legacy receipts: their recorded immutable originals), and the declared formal math/proposal/routine contracts, repairing derived STATUS only; unreadable or inconsistent receipts are refused, never re-blessed. There is no `impact.md` ledger and no `evidence_packs:` frontmatter — legacy packs and ledger entries stay untouched historical bytes.
- Every Project has a vault-only `mathdocs/` registry: stable Math Derivations carry the current script SHA-256, Python/SymPy versions, verification time, host, and source directory; stable regular notes mark each display equation with a resolvable `MathDoc` result or exposition identifier.
- Task P proposal artifacts use `draft -> approved -> done` status and `pending -> accepted|rejected` decisions; `validate-proposal` enforces the SHA-pinned curated input manifest, scope/independence policy, immutable fingerprints, behavioral evidence, and project-relative candidate isolation, and `check-completion` enforces the proposal gate before its Consumer Interface early return.

## Details
- `validate` checks notes, MathDocs, proposals, and projections; retired pack and ledger inputs are neither required nor audited, and legacy pack/ledger bytes stay untouched.
- `ProjectEntry.history_integrity` selects exact canonical Project-relative records for retrospective reporting only (`mode: warn|strict`, default `warn`). Warn selection precedes receipt/pin readers and preserves the claimed lifecycle with `unverified — not audited`; selected old done claims are not reopened solely for missing modern proof, while approved/draft claims remain visible. Strict inspection verifies the existing receipt and proposal input/fingerprint contracts and fails on missing or mismatched integrity without rewriting records, receipts or pins. Canonical STATUS follows configuration, not an invocation override; unselected/current checks and all operational authority, execution and publication gates remain strict. Historical display never grants completion or mutation authority.
- `validate --history-audit` forces strict retrospective checks only for that invocation and only for a non-empty configured history scope; absent or empty scope is refused. It is read-only: records, receipts, pins and canonical STATUS bytes are unchanged, and subsequent generation still uses the configured view. Success means the selected records passed invocation-time integrity checks, not that all history is verified or that completion proof or operational authority was granted.
- `check-math` runs active derivations in lexical order with a bounded timeout, comparing their versioned JSON protocol, environment, source hash, and named results against the paired notes; execution is trusted, not sandboxed. `check-math --update --source-root` publishes the complete `mathdocs/` tree or nothing; dependents update from the published canonical results before rerunning `validate` and completion.
- Math-derived work items declare `derivations` plus a finite `math_implementation_files` list; `check-completion --source-root` requires each listed file to stay under that root and carry an adjacent `MathDoc: project/slug[#result]` identifier.
- Completion is record-local: `related_notes`, the record's `derivations`, and those notes' declared derivations form the checked closure; unrelated legacy defects do not block it, while declared missing, malformed, deprecated, or stale dependencies do. Identity, ancestry, acceptance, review, containment, and receipt gates are unchanged, and non-mathematical records need no unrelated mathdocs registry.
- Finding responses are optional worker claims in the existing completion ledger: `worker_response` has `kind: fixed|refuted|blocked` plus non-empty `detail` and `evidence`; a blocked response identifies its prerequisite in detail and escalation rationale in evidence. A response never closes a Blocking finding. Reviewer acceptance keeps `status: resolved`, optionally `resolution: fixed|refuted`; supplied resolution must agree with the resolved row. Legacy closed rows and risk acceptance remain valid without new fields. Completion checks annotation shape, not reviewer authentication.
- The checked completion sequence keeps an authorized `approved`/`in_progress` work phase while the independent review decision lives in `completion_review`; review approval is not lifecycle completion. Native `work finish` refuses `status: review` with `WORK_PHASE_DENIED` and alone publishes receipted `done`. Coordinator guidance must preserve this existing admission rule rather than strand a reviewed record in an unsupported finish phase.
- Completion drafting is read-only: `work prepare-completion --work-record REF` prints the identity, canonical record path and criterion drafts in record order. Authored entries retain every field, including adverse findings; unauthored criteria stay blank. Existing nonterminal Story/Quick Task authorization and malformed/duplicate criterion refusals remain. No observations, outcomes, reviewers or approvals are manufactured.
- Optional explicit `--worktree` adds only top-level `source_revision`, using finish's shared binding algorithm and its same-root/nested/external boundaries. Exactly the canonical Project's `.kosmic/create.lock` is command-owned finish output and, for same-root Projects only, excluded from the digest; unrelated `.kosmic/` data and an external Project's writer-local lock remain bound. Omission preserves the old payload and never infers a writer from the current directory. Both paths write nothing and have no `--write` mode. The digest is a point-in-time observation, not Git HEAD or cached permission: finish still rejects source drift and incomplete proof.
- Consumer completion checks whole Skill Pair integrity and the current source or routed reference for each declared Consumer note. Projection generation and unscoped `check-math` retain their strict current-domain checks; historical inspection changes reporting, not those admission rules.
- `check-installation` byte-compares both named-adapter packages and Project identity against the canonical pair; success proves on-disk installation only — reload the adapter and inspect its skill inventory before claiming active-session discovery.

### Existing library role recovery
`migrate-library` accepts the existing `kosmic.semantic-role-classification/v1` map for in-place legacy Topic metadata recovery: each source names its unchanged library-relative identity, an explicit role, and typed relationships, and an optional `source_project` pin must match existing provenance. Unclassified legacy dependencies and symlink sources or generated outputs are rejected; recovery preserves body bytes, validates the staged library, and publishes atomically. It cannot turn an incomplete paragraph into a valid procedure — a separately approved and reviewed content proposal must supply that repair.

## Flat-spec migration
`migrate-subprojects-plan` saves an exclusive, hash-pinned JSON plan deriving feature owners from declared ancestry and explicit assignments; it never approves work or moves records. `migrate-subprojects-apply` requires the exact reviewed plan digest and a currently approved or in_progress Quick Task in that Project, recomputes the plan, rejects drift and occupied or unsafe targets, validates a staged catalog, and publishes checked per-path changes with durable before images; `migrate-subprojects-recover` reconciles an interrupted transaction, and unknown external edits are conflicts, not permission to overwrite. Application requires a Git worktree with its managed `.tmp/` scratch root ignored; migration execution and adapter installation retain separate approvals, and a migration receipt is not a work-completion receipt.

Planning audits every authoritative Markdown file, including root documents, specs, notes, and MathDocs. Proposal input manifests and curated snapshots under `specs/skill-proposals/inputs/` are protected evidence — pinned, audited, never rewritten; evidence, logs, and generated skills are likewise pinned and never rewritten. A broken reference is repaired only when its filename or stem has exactly one authoritative target; ambiguous matches block application, and `link_corrections` and `link_problems` record every outcome. Frontmatter parsing supports nested mappings and sequences, flow collections, and literal/folded block scalars without third-party YAML; duplicate keys, anchors, aliases, merge keys, complex keys, and tab indentation are rejected. For `linked_*` metadata a document-relative destination takes precedence over a Project-root namesake, so an existing owner's link keeps resolving when a root-level namesake is also migrated; staged catalog validation verifies owner ancestry before publication even when the plan reports no ownership ambiguity.

## Derived STATUS authority
`generate-status --work-record REF` regenerates the derived `STATUS.md` in the Project's bound status root; the only written path is that STATUS file — records, receipts, and sources are never written, and hand edits are regenerated over. Implementation records keep their exact legacy grants: an approved or in_progress story or quick-task authorizes the refresh unchanged, including project-level quick-task authority against a fixed-subproject bound directory. Bounded planning records additionally authorize this one derived refresh: an approved PRD or Architecture, or a draft PRD, Architecture, Epic, or Story whose own hierarchy governs the bound output path — with a Project-wide status root, or a registered directory fixed to the record's own subproject; a draft story additionally requires its approved ancestry. Everything else is refused `WORK_PHASE_DENIED` and nothing is written. A draft never narrows the Project-wide rendered view, planning grants no source mutation or `work finish` capability, and the status-root binding is never created, replaced, or dropped by a refresh.

## Optional knowledge curation
An optional three-stage curation routine — `curation-prepare` (deterministic selection) → agent semantic review recorded in the governing work record → `curation-finalize` (deterministic verification) — nominates skill-material candidates between manual or externally scheduled runs. Prepare freezes the cutoff `U` at run start, takes the first lower bound explicitly (`--from <exact-UTC>` or `--baseline`), and selects notes with `L < changed_at <= U` by semantic `updated` (created fallback); the reserved `index.md` is never selected. The persisted per-scope checkpoint advances to exactly `U` only after a full-scope successful finalize; subset runs and failures never advance it. Review is agent work, not CLI: nominations follow the existing proposal/review records, and the routine never auto-approves, publishes, installs, or schedules anything. Interface and details: `skills/references/curation_routine.md`.
