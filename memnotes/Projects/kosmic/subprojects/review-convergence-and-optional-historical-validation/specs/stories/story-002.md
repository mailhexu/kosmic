# Story 2: Read-only strict-audit override and compatibility cutover

## User Story

As a Project maintainer,
I want a single read-only `validate --history-audit` override that forces retrospective strict auditing of exactly my configured history scope for that one invocation — with an empty-scope refusal, immutable history/STATUS bytes, and zero new flags on any active command,
So that I can fail loudly on real historical mismatches on demand while every operational surface and the canonical view stay exactly as Story 001 defined them.

## Scope

### In Scope
- Adding `--history-audit` to the existing `validate` subcommand only: read-only forced strict audit of the configured non-empty scope, refusing clearly when no/empty scope is configured; existing validate exit conventions retained.
- Compatibility cutover sweep: every operational command/loader (work finish/check-completion, validate-proposal, migration, math, library, workdir, proposal/routine readers) accepts history configuration with unchanged behavior and gains no flag; audit state never reaches operational paths.
- Immutability guarantees: the audit renders no alternate canonical STATUS, writes no history, and diagnostics never claim "all history verified".
- Consumer docs/knowledge coherence in the same episode: `skills/references/cli-projection-commands.md` command reference, `notes/cli-projection-commands.md` durable invariant, `notes/cli-extension-conventions.md` contributor guidance (body link), plus native projection refresh of the published note; real end-to-end smoke.

### Out of Scope
- New history selectors/flags beyond `validate --history-audit`; any mutation, backfill, auto-repin, lifecycle rewrite, or authority grant from audit results; changes to warn-mode behavior delivered by Story 001; upstream code-review skill edits; permanent prose/call-count/wiring tests; changes to the separate review-convergence Epic.

### Owned Files
- `skills/scripts/kosmic_project_skills.py` (validate parser/dispatch), `skills/scripts/kosmic_history.py` (audit override param wiring), `skills/references/cli-projection-commands.md`, `notes/cli-projection-commands.md`, `notes/cli-extension-conventions.md`. Shared publication (`kosmic_completion.py`) and CLI knowledge/generated outputs are reconciled by the parent integration owner against one baseline — one writer per shared path, no blind whole-file edits; Story 001 must be resolved with its native receipt before this Story's edits begin.
- `skills/scripts/kosmic_dreams.py`: compatibility-cutover repair of the established optional-catalog flat receipt path, exposed by integrated navigation and real finish-retry regressions; no new reporting or authority contract.

## Acceptance Criteria

- [x] AC1: Given a configured non-empty `history_integrity` scope, when `kosmic_project_skills.py validate --history-audit --project …` runs, then it forces retrospective strict audit of exactly the configured records for that invocation and fails under existing validate exit conventions on actual missing/mismatched integrity with integrity-specific diagnostics, regardless of whether configured mode is warn or strict.
- [x] AC2: Given no or an empty configured history scope, when `validate --history-audit` runs, then it is refused as a clear configuration/usage error (nonzero exit, explicit message) rather than reporting an audit of nothing.
- [x] AC3: Given a warn-mode Project, when `validate` runs without the flag, then behavior is exactly the Story 001 contract and the flag is the only strict override; canonical generation before and after the read-only audit uses the same configured view with identical bytes, the audit never renders an alternate canonical STATUS nor writes history, and the audit flag is neither accepted by nor passed to the generator.
- [x] AC4: Given the audit or normal validate on a history-configured Project, when before/after byte hashes are compared, then configured records, receipts, pins and bound `STATUS.md` are identical, warn-path diagnostics say `unverified`/`not audited` (never "verified"), and audit success states only that configured records passed invocation-time integrity — granting no completion proof or authority.
- [x] AC5: Given an active stale/tampered in-scope artifact, when `validate --history-audit` or strict-configured validate runs, then existing strict freshness/identity/ancestry/pin failures still refuse it — the history override never bypasses an active dependency and never grants mutation authority.
- [x] AC6: Across `work finish`, `check-completion`, `validate-proposal`, migration, math, library, workdir and operational loaders on a history-configured Project, when each command runs, then behavior and exit codes match the no-policy baseline and no command except `validate` gains any history flag (verified against `--help` surfaces).
- [x] AC7: Given a faithful disposable copy of the kosmic Project under managed scratch with the three representative records selected in that copy's `history_integrity`, when the real CLI runs warn `validate`, `validate --history-audit` and `generate-status` on the copy, then warn validation follows the Story 001 success path with unverified warnings, the audit fails on the old done record's missing receipt, generation bytes are identical before and after the audit, every record/receipt/pin/STATUS byte in the copy is unchanged, and the live Project's ProjectEntry and history bytes are untouched.
