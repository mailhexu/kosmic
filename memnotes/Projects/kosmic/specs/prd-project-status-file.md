# Project Status File

## Problem Statement

A Kosmic-managed working directory keeps its spec state only inside the vault
(`specs/INDEX.md` and spec frontmatter). An agent that starts in the working
directory sees AGENTS.md but not the current spec picture. It must open the
vault to learn which stories are open, which specs are approved, and what is
in flight. The working directory has no self-describing status surface.

## Goals

- One generated `STATUS.md` at each managed project's working-directory root.
- The file records the current status of every spec: PRDs, Architectures,
  Epics, Stories, Quick Tasks, and Skill Proposals.
- Deterministic generation from vault spec frontmatter — no hand editing.
- Created at initialization (Task 1) and referenced from AGENTS.md.
- Regenerated whenever a spec is created or its status changes, as a
  mandatory workflow step.

## Non-Goals

- Runtime or test status, build state, or anything not derived from specs.
- Automatic filesystem watching; regeneration is an explicit command the
  workflow requires.
- Replacing `specs/INDEX.md` (the vault index remains authoritative).

## Functional Requirements

| ID | Requirement | Priority |
|----|-------------|----------|
| FR-S1 | `generate-status --project {PROJECT} --root {WORKING_DIR}` writes `STATUS.md` at the working-directory root from vault spec frontmatter. Identical vault state produces byte-identical output. | must |
| FR-S2 | `STATUS.md` contains: project id, generation timestamp marker (vault head commit, not wall clock), and one table per spec class (PRD, Architecture, Epic, Story, Quick Task, Skill Proposal) with name, link to vault spec, status, and updated date; plus an Open Work summary line counting nonterminal records. | must |
| FR-S3 | Task 1 (Initialize) generates the first `STATUS.md` and the AGENTS.md integration section references it. | must |
| FR-S4 | Tasks 0, 5, 6, and 7 mandate `generate-status` after any spec creation or status transition; the story/spec workflow lists it as a required step. | must |
| FR-S5 | `validate --project` fails closed when `STATUS.md` exists at the configured root and differs from generated bytes (drift detection), and warns when spec state changed but no root is configured. | must |
| FR-S6 | The project root binding is recorded in `ProjectEntry.md` (`status_root:`), set at initialization; migration adds it to existing projects. | must |
| FR-S7 | `migrate` and `init` accept the root argument and keep STATUS.md absent (not failed) when no root is bound. | should |

## Non-Functional Requirements

| ID | Requirement | Priority |
|----|-------------|----------|
| NFR-S1 | Generation is offline, deterministic, and reads only spec frontmatter. | must |
| NFR-S2 | STATUS.md uses relative standard Markdown links into the vault and STE-style prose. | must |

## Success Criteria

- [ ] Initializing a fixture project creates AGENTS.md integration plus a STATUS.md matching its spec set.
- [ ] Flipping a story status and running the workflow step updates STATUS.md; hand edits are caught by validate drift detection.
- [ ] Two runs over identical vault state produce identical bytes.
- [ ] Unbound projects behave exactly as before (no failure, warning only).
- [ ] Full suite, gates, and adapter checks remain green.

## Open Questions

- [x] Should the Open Work summary also list dream-flagged items, or stay spec-only? — **Spec-only** (AD-S5): dreams are vault-level reflection, not project spec state.
- [x] Multi-project directories — **Out of scope** (AD-S5): one `status_root` per ProjectEntry; a directory shared by two projects binds none and gets the warning path.
